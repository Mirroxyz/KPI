# Журнал взаємодії з AI (Prompt History) - Лабораторна робота №2

## Ітерація 1: Структурування вимог для бібліотеки

**Промпт:**
> "На основі ER-моделі міської бібліотеки з Лабораторної роботи №1 сформуй акторів, EARS-вимоги, User Stories і Gherkin-сценарії для процесів автентифікації, бронювання, видачі, повернення та сповіщень."

**Отриманий результат від AI:**

Було визначено узагальненого актора `User`, спеціалізації `Member` і `Librarian`, а також зовнішню систему `EmailService`. Створено сім вимог `REQ-01` - `REQ-07`, п'ять User Stories і чотири Gherkin-сценарії. Вимоги пов'язані з сутностями `MEMBER`, `BOOK`, `BOOK_COPY` і `LOAN` з першої лабораторної.

**Проблема/Критика:**

Початкові формулювання на кшталт «The system should send an email» не містили чіткого тригера, одержувача, каналу та перевірюваного вмісту. Також формулювання «calculate a penalty» не вказувало, до якої операції та сутності належить штраф.

**Коригувальний промпт:**
> "Перепиши EARS-вимоги у формі WHEN або WHILE ... SHALL. Для кожної вимоги вкажи конкретний тригер, актора, об'єкт, результат і зовнішню систему. Пов'яжи штраф із простроченим LOAN та BOOK_COPY, а сповіщення - з Member і EmailService."

**Фінальний результат:**

`REQ-04` тепер створює штраф після повернення простроченого `BOOK_COPY` і прив'язує його до `LOAN`, а `REQ-05` визначає надсилання листа через `EmailService` із назвою книжки та строком отримання.

## Ітерація 2: User Stories і Gherkin-сценарії

**Промпт:**
> "Сформуй User Stories за шаблоном As a... I want to... So that... і додай Given/When/Then-сценарії, які перевіряють основні позитивні та негативні потоки бібліотеки."

**Отриманий результат від AI:**

Підготовлено історії для автентифікації, бронювання, операцій бібліотекаря, прострочення та сповіщення. До них додано сценарії успішного бронювання, блокування бронювання через штраф, пізнього повернення та виконання бронювання.

**Проблема/Критика:**

У першій версії сценарії змішували бібліографічну сутність `BOOK` із фізичним примірником `BOOK_COPY`, а результат сповіщення не містив критерію перевірки доставки.

**Коригувальний промпт:**
> "Уточни Given/When/Then так, щоб операції видачі та повернення посилалися на BOOK_COPY і LOAN, бронювання - на BOOK, а сценарій сповіщення перевіряв EmailService, назву книжки та collection deadline."

**Фінальний результат:**

Gherkin-сценарії узгоджено з ER-моделлю: `BOOK_COPY` використовується для видачі, `LOAN` - для історії, а `BOOK` - для бронювання.

## Ітерація 3: Побудова Use Case діаграми

**Промпт:**
> "Створи Use Case діаграму для акторів User, Member, Librarian і EmailService. Покажи узагальнення акторів, include для обов'язкової автентифікації та extend для умовної оплати штрафу."

**Отриманий результат від AI:**

Перший варіант було записано з ключовим словом `usecaseDiagram`, акторами, овальними Use Cases та UML-подібними стрілками.

**Проблема/Критика:**

Синтаксис `usecaseDiagram` не підтримується Mermaid і не може бути відрендерений стандартним Mermaid-рендерером. Крім того, у чернетці напрямок `extend` був прочитаний неоднозначно: розширювальний Use Case має посилатися на базовий.

**Коригувальний промпт:**
> "Перепиши Use Case діаграму на валідний Mermaid flowchart. Представ акторів вузлами, Use Cases овальними вузлами, збережи generalization, include і extend. Напрямок extend зроби від Pay Fine до Return Book."

**Фінальний результат:**

`use-case.mmd` використовує `flowchart LR`, містить узагальнення `User` до `Member` і `Librarian`, `include` для `Authenticate` та `extend` від `Pay Fine` до `Return Book`. `EmailService` підключено до `Send Notification`.

## Ітерація 4: Трасування та аудит

**Промпт:**
> "Побудуй матрицю трасування REQ-01 - REQ-07 до User Stories, Use Cases і Gherkin-сценаріїв. Забезпеч багато-до-багатьох зв'язки та залиш одну вимогу свідомо непокритою."

**Отриманий результат від AI:**

Створено `traceability.md` з таблицею трасування, де одна вимога може мати кілька сценаріїв, а один сценарій може перевіряти кілька вимог. `REQ-07` про щомісячний статистичний звіт залишено зі статусом `Out of scope`.

**Проблема/Критика:**

Чернеткова матриця містила переважно зв'язки 1:1 і не пояснювала, чому аналітична вимога не реалізована. Також аудит мав окремо перевірити семантику `include`/`extend` і відповідність сутностям першої лабораторної.

**Коригувальний промпт:**
> "Заміни 1:1 трасування на багато-до-багатьох, додай пояснення для REQ-07 як Out of scope, перевір напрямки include та extend і звір Member, BOOK_COPY та LOAN з Лабораторною роботою №1."

**Фінальний результат:**

Матриця містить багато-до-багатьох зв'язки, а `AUDIT.md` документує виправлення неоднозначностей EARS, Mermaid-помилки та розбіжності між Use Cases і ER-моделлю.

## Ітерація 5: Senior BA Review та рефакторинг

**Промпт:**
> "Проведи фінальний бізнес-аудит покриття Lab 2. Перевір, чи має кожен ключовий Use Case власний Gherkin-сценарій, чи правильно узагальнені актори та чи не залишився Search Catalog сиротою. Окремо перевір, що REQ-01 тестується сценарієм Authenticate, а не лише Given-передумовами."

**Отриманий результат від AI:**

Виявлено прогалини в покритті `Authenticate`, `Search Catalog` і штатного повернення без штрафу. Також виявлено, що `REQ-01` помилково трасувалася через сценарії бронювання, а `User` не мав прямих зв'язків із `Authenticate` та `Search Catalog`. Додатково зафіксовано розбіжність між Use Case `Pay Fine` і відсутністю сутності `FINE` у моделі даних Лабораторної роботи №1.

**Проблема/Критика:**

Автентифікація як `Given` описувала стан, але не перевіряла саму операцію. `Search Catalog` був представлений у документах неповно, а сценарій повернення із простроченням не містив формули штрафу. Спеціалізовані актори також мали дубльовані або неповні зв'язки з каталогом.

**Коригувальний промпт:**
> "Додай REQ-08 для пошуку, окремі User Stories і Gherkin-сценарії для Authenticate, Search Catalog, on-time Return Book та Pay Fine. Зміни REQ-01 на User, REQ-06 на обмеження для Librarian, додай прямі зв'язки User до Authenticate і Search Catalog, а Member до Pay Fine. Онови трасування, бізнес-аудит і захист."

**Фінальний результат:**

Оновлені `spec.md`, `use-case.mmd`, `traceability.md`, `AUDIT.md` і `DEFENSE.md` тепер узгоджено покривають ключові потоки. `REQ-01` має лише пряме покриття сценарієм автентифікації, `REQ-08` покриває пошук, а відсутність `FINE` винесено в план наступної ітерації.
